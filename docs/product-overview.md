# 产品定位与普通邮箱接入对比

整理日期：2026-09-11。本文区分腾讯 Agent Mail 提供的邮件能力、本项目已经实现的流程，以及后续计划。

## 如何介绍本项目

> 我们正在搭建一个支持人工审核的邮件事务助理。目前使用腾讯 Agent Mail 作为邮件接入渠道：按已确认资料处理常见事项，复杂事项交给负责人决定，在飞书审核准确回复后再发送。后续可以适配现有工作邮箱。

产品价值在于业务处理规则、人工介入和可追踪的执行过程。邮箱是来信人与助理之间的通信入口，来信人无需安装 Agent 或使用接收方的飞书审批系统。

## Agent Mail 和普通邮箱有什么区别

普通邮箱开放 IMAP/SMTP 或厂商 API 并完成授权后，也可以接入 Agent，实现同类工作流。授权码只解决访问权限，业务理解、持续运行与人工审批需要另外实现。

腾讯 Agent Mail 提供与个人邮箱隔离的邮箱服务，以及 CLI、Skill、OAuth 授权、收发搜索和附件操作。它降低 Agent 的接入成本；发送的两阶段确认也不是业务负责人真人审批。[腾讯官方功能说明](https://github.com/Tencent/AgentlyMail/blob/main/README.md)

| 比较项 | Agent Mail | 普通邮箱接入 Agent |
| --- | --- | --- |
| 收发、搜索、附件 | 通过官方 CLI 调用 | 通过标准协议或厂商 API 调用，具体能力依服务商 |
| Agent 使用说明 | 已有官方 Skill | 选用已有插件/Skill，或自行编写 |
| 独立工作身份 | 提供专属邮箱 | 可以另外开设工作邮箱 |
| 授权 | 官方 OAuth 流程 | 按服务商使用授权码、OAuth 等方式 |
| 业务知识与 001—005 规则 | 需要外部 Agent 和工作流 | 同样需要 |
| 飞书审批与执行记录 | 本项目另外实现 | 可适配同样的设计 |
| 全天处理 | 需要持续运行的业务服务 | 同样需要 |

OAuth 也不是 Agent Mail 独有。Gmail 的标准 IMAP/POP/SMTP 接口支持 OAuth 2.0；不能仅凭采用 OAuth 就判断整个业务流程更安全。[Google 官方协议说明](https://developers.google.com/workspace/gmail/imap/imap-smtp)

## 封装具体省掉哪些步骤

以下比较对象是“尚未有邮件连接工具的 Agent”，不是已经装好成熟邮件插件的 Agent。

| 接入工作 | 直接接普通邮箱时需要处理 | Agent Mail 的封装 |
| --- | --- | --- |
| 连接配置 | 选择协议/API，配置服务器、端口、加密连接 | CLI 使用固定命令，无需手动配置 IMAP/SMTP 服务器 |
| 授权接入 | 按服务商要求集成授权流程与凭据使用 | `auth login` 引导授权，`+me` 核验邮箱 |
| 邮件工具 | 用库或接口封装列表、读取、搜索、发送与回复 | 提供对应 CLI 命令 |
| 邮件格式 | 解析正文、收件人与附件，构造发送请求，处理编码 | CLI 提供相应参数与结果，减少直接处理协议和格式的工作 |
| Agent 调用说明 | 描述工具、参数与操作步骤 | 安装官方 Skill 即可获得使用说明 |
| 发送确认机制 | 自行设计准备与执行步骤 | 官方支持两阶段确认；真人审核仍需另建 |

官方接入流程为：安装 CLI → 安装 Skill → 浏览器 OAuth 授权 → `+me` 验证。[官方安装文档](https://agent.qq.com/doc/cli-setup.md)

这是接入工程的简化，不代表免去账号授权、业务权限、连接故障处理和结果验证。如果普通邮箱已有成熟插件，同样可以只填连接信息并授权，Agent Mail 的增量便利会缩小；不宜把所有普通邮箱方案都按从零开发估算。

## 本项目的职责分工

| 层次 | 负责什么 | 当前实现或边界 |
| --- | --- | --- |
| 邮件服务 | 存储、读取和提交邮件 | 腾讯 Agent Mail + agently-cli |
| 业务判断 | 依据知识库理解来信、选择模板或提出待确认问题 | 活跃 Agent 会话配合 demo/live 资料；发送脚本不独立判断业务语义 |
| 授权执行 | 核对邮箱、白名单、主题、期限、次数、准确草稿和去重台账 | mail_guard.py |
| 人工审核 | 完整正文展示、修改保存、批准或拒绝、版本校验 | feishu_review.py；004 业务决定仍先在控制会话中确认 |
| 回调常驻 | 接收飞书按钮事件、管理审批队列和卡片期限 | feishu_service.py + Mac mini LaunchAgent |
| 全天业务运行 | 持续收件、调用模型判级、调度与运行告警 | 待建设；常驻回调不等于全天自动收发 |

001—005 是接收方内部规则，不要求来信人填写；邮件里自称某个等级不能改变授权。完整定义见[人工介入规则](review-levels.md)。

## 当前可演示与未完成事项

- 已验证限时场景下的整理、模板回复提交、真人批准后提交、业务决定后回复和越权阻断。
- 本机飞书修改、重新审核、拒绝和自动到期已验证；Mac mini 已验证发卡、过期后持续在线和进程正常终止后恢复。
- Mac mini 真人按钮回调迁移验证与邮箱授权待完成，真实邮件执行仍关闭。
- 邮件服务接受发送任务不等于最终投递，已有回信仍需同事核对收件；不为补验证重复发送已提交邮件。
- 全天收件与模型调度、真实业务知识、完整运行告警，以及断网/断电/系统重启验证仍待完成。

以上是截至整理日的验收记录。完整证据与后续顺序见[测试状态](test-status.md)，实时服务状态按[运维文档](macmini-service.md)检查。

## 对外产品形态

来信人需要知道服务范围、邮件示例、补充信息方式、等待人工确认的含义和人工联系渠道。试用版见[来信人说明](sender-guide.md)。首次欢迎回执、等待状态通知及网页帮助入口目前属于产品建议，尚未上线。

后续若接入学校或公司的普通邮箱，可以保留业务规则和审批设计，但需要适配邮件接口、账号授权、邮件标识和发送结果，并重新验证去重与审批执行。当前仓库还没有通用的多邮箱连接层，不能直接替换一个授权码就宣称迁移完成。
